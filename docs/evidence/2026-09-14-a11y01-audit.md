# Evidence — assistive audit of the student flow (A11Y-01 / AC-24, 14 Sep 2026)

## Scope

Student search → result → live status on `/student` (web app): screen-reader semantics, `aria-live` announcements for
state changes, focus after search / select / back, keyboard access to the map overlay controls, and layout at 200 % text
size and 360 px width. Target: WCAG 2.2 AA. The task allowed fixing findings in place; everything not fixed is listed
under **Known limitations** with the reason.

## Method (credential-free, real code paths)

- Web app served by the normal Vite dev server; Firebase **Auth emulator** with one approved student; `/api` answered
  by an in-page mock whose tracking feed can be switched between `live`, `delayed` and `offline` (status and timestamps
  consistent, as the real API computes them).
- Headless Chromium (playwright-core 1.49, software WebGL) in three contexts: desktop 1280×900; phone 360×740
  (touch/mobile emulation) including a simulated **200 % text size** (`documentElement.style.fontSize = 200 %`); and
  640×450 CSS px, which is a 1280 px desktop at **200 % browser zoom**.
- Per view: axe-core 4.10.3 (WCAG 2.x A/AA + best-practice tags), Chromium's accessibility tree snapshot, a Tab walk
  recording every stop's role, accessible name and visible focus ring, `document.activeElement` after each step, a
  `MutationObserver` over every live region during steady state and three status transitions, and layout probes
  (horizontal overflow and its culprits, overlay-vs-zoom-control overlap, headline clipping, targets under 44 px, bottom
  nav label clipping) with screenshots.
- Automated: `artifacts/pu-transit` vitest 84/84 (new: focus targets, repeated-search and unrelated-re-render focus,
  single announcer text in `student.test.tsx`; no stale feed across a bus change in `use-transit.test.tsx`; one fleet
  announcer in `fleet-tab.test.tsx`), `tsc` clean.
- Throwaway harness (git-ignored): `.local/a11y01-harness/` (`run.mjs`, before/after reports and screenshots).

**Not tested**: a real screen reader (NVDA/JAWS/VoiceOver/TalkBack), physical devices, Firefox/Safari focus-visible
behaviour. The announcer and focus targets are verified in the accessibility tree and `activeElement`, not by ear.

## Findings

### P0 — none

### P1 — fixed

| # | Location | Finding | WCAG | Fix |
| --- | --- | --- | --- | --- |
| 1 | `index.html` viewport meta | `maximum-scale=1` blocked pinch zoom (axe critical `meta-viewport`) | 1.4.4 | attribute removed |
| 2 | `StateTile` (`role=status aria-live=polite`), used on student, driver and admin fleet | age line ticked every second and the tile remounted per sample → a screen reader hears "live 4 s ago, live 5 s ago …" indefinitely; real state changes buried; the fleet tab held one such region per bus | 4.1.3 | tile is no longer a live region; each page owns one `sr-only` `role=status` line whose text is only the state word — student "bus 1234: delayed", driver the state label, admin fleet the counts ("fleet: 2 live, 1 offline") — so it changes exactly once per transition |
| 2b | `useTrackingFeed` on a bus change | for one render the hook still returned the previous bus's feed, so the new announcer would have said "bus B: <A's state>" before B's first poll (found in code review, not by the harness, which only transitions one bus) | 4.1.3 | the hook tags its state with the bus it was fetched for and returns the empty state until the new bus answers (`use-transit.test.tsx`) |
| 3 | `student.tsx` search / result / back | focus never moved: after Enter it stayed in the input (results below unannounced), tapping a result or "back to results" on the phone dropped focus to `<body>` | 2.4.3, 3.2.2 | a focus request in state (fresh object per request, effect keyed on it): focus moves to the bus heading (single match or selected result), the results count / no-match tile (multi / zero), or back to the result tile that was open (`id="bus-{routeId}"`); a repeated identical search moves it again and unrelated re-renders never move it |
| 4 | `map-view.tsx` markers | stop, bus, campus and viewer markers were unnamed `role=button` tab stops (axe serious `aria-command-name`); the bus SVG was an unnamed image | 4.1.2, 2.4.4 | `keyboard={false}` on every marker (the stops list under the map is the non-map equivalent), bus glyph `aria-hidden` |
| 5 | Leaflet container | `tabindex=0` `div` whose accessible name was the whole map text ("123+− Leaflet \| OpenFreeMap …") | 4.1.2 | `role=region` + `aria-label="route map"` set on mount |

### Positive findings (kept)

Global 3 px `:focus-visible` ring at 3 px offset on every control, including the headings that now receive focus;
skip link; `nav aria-label="app bar"` + `main#main`; `role=search` form with a labelled input; shift picker is a
`role=group` of `aria-pressed` toggles; result tiles have full accessible names (bus number, shift, origin → destination,
pressed state); the ordered **stops list** under the map is a complete non-map equivalent of the route; the status
hint ("position is fresh", "…not updating") is visible text, not colour only; `prefers-reduced-motion` disables the
tile flips; no colour-contrast violations in any view; 640 px (200 % browser zoom on a desktop) lays out cleanly.

## Owner walkthrough (real assistive technology)

1. Phone with TalkBack or VoiceOver: open `/student`, search a bus with one match, expect the focus/announcement to land
   on "bus NNNN"; leave the screen open while the driver's trip goes stale, expect exactly one announcement per state
   change ("bus NNNN: delayed" → "offline" → "live") and no periodic chatter.
2. Same phone at the OS's largest font size: no horizontal scrolling on search or route view; the "my location" tile
   shows only its icon and never covers the zoom control; the search tile sits under the input.
3. Desktop with NVDA: Tab into the map — expect "route map, region" then zoom in / zoom out, never bare "1", "2", "3".
