# Route publishing (RTE-01, RTE-02, RTE-03) — 13 Sep 2026

Closes ADM-02's remaining gap: a route can no longer reach riders with a path nobody verified, and when an admin knowingly publishes an unverified path, riders are told.

## Data

`routes/{id}` gains two fields (OpenAPI `Route` / `RouteInput`, API `routes/transit.ts`, Rules):

| field | values | meaning |
| --- | --- | --- |
| `status` | `draft` \| `published` (required) | Drafts are returned to admins only; `GET /api/routes` filters them out for everyone else. Records written before RTE-01 have no `status` and are read as `published` (they were always visible). RTE-02 will extend this field with `archived`. |
| `pathSource` | `ors` \| `manual` \| absent | `ors`: `pathData` is provider road geometry plotted through **every stop in order**. `manual`: the admin ticked *manual path*, acknowledging the drawn line is not road-verified. Absent: unverified — allowed on drafts and on pre-RTE-01 records only. |

## Gate

The API refuses with **409 `ROUTE_PATH_UNVERIFIED`** (nothing written) when:

- `status == published` and `pathSource` is absent, or
- `pathSource == ors` (any status) and `pathData` has fewer than two points or **any stop is more than 150 m** from the polyline (`api-server/src/lib/route-path.ts`, flat-earth point-to-segment distance; the message names the stops and their distance).

The `ors` claim is checked on drafts too, so a stale endpoint-only path can never be published later as a verified one. Rules mirror the coarse gate (`status` required and enumerated; `published` needs `manual`, or `ors` with a non-empty `pathData`); the 150 m check is API-only.

## Editor (`pages/admin/routes-tab.tsx`)

- *plot road path* sends the stop list as `start` / `via` / `end` to `POST /api/geo/directions` (max 50 stops, ORS limit) and marks the draft `ors`. It needs at least two listed stops: the first is the start and the last is the end. (Until 14 Sep it geocoded the typed start/end places when fewer than two stops were listed; that path is gone — stops are added by place search, pasted coordinates or map tap, and the rider-facing start/end labels follow the first and last stop until edited by hand.)
- Adding, removing or reordering a stop (new arrow buttons) clears `pathData` and drops `ors`; renaming a stop does not. A ticked *manual path* survives stop edits.
- *publish* is disabled until the draft is `ors` or *manual path* is ticked; *save draft* always works. A server 409 is shown as the form error.
- Admin list shows `draft · hidden from riders` and `path not verified`.

## Riders (`pages/student.tsx`)

`path not verified` appears in the result list and the route header whenever `pathSource !== 'ors'` — manual routes and every pre-RTE-01 route until an admin re-plots it. The map keeps drawing dashed straight segments when `pathData` is empty.

## Versions and drafts (RTE-02, ADM-03 / AC-19)

Data:

- `routes/{id}` is always what riders read: the published content, `status` (`draft` | `published` | `archived` — archived is accepted everywhere and hidden from riders; the archive action itself is RTE-03) and `publishedVersion` (absent on routes published before versioning).
- `routeVersions/{routeId}/{n}` — immutable snapshot written at each publish (`n`, shift, bus, origin, destination, stops, pathData, kind, pathSource, `createdAt` server time, `createdBy` uid). Admin create-once (Rules refuse a second write to the same `n`, updates and deletes), member read. Kept when the route is deleted.
- `routeDrafts/{id}` — pending edits of a rider-visible route, admin-only in Rules. Admin `GET /routes` merges them over the node and marks `hasDraft: true`; riders never see them.
- `GET /routes/{id}/versions/{n}` returns one snapshot (member).

`POST /routes` decides by the request's `status`:

| request | route never published | route published (or archived) |
|---|---|---|
| `draft` | overwrite `routes/{id}` (status draft, hidden) | write `routeDrafts/{id}` only; riders keep the node |
| `published` | RTE-01 path gate, then one atomic root PATCH: node with `publishedVersion = 1`, `routeVersions/{id}/1`, draft cleared | same with `n = publishedVersion + 1` |

Audit stays `route.save`; the summary ends with `published vN`, `draft` or `draft saved; riders keep vN`.

Trips: Start writes `feed.routeVersions = { routeId: publishedVersion }` for every published, versioned route of the bus (omitted when there is none). Rules check each pin at Start against the route node itself (same bus, status published, equal to its current `publishedVersion`), so a driver client cannot forge one; after Start the map cannot change, gain keys or be dropped whole for the rest of the trip; the next Start pins whatever is published then. The student page, while the feed is `active` and the pinned number differs from the route's `publishedVersion`, fetches that snapshot and renders its stops/path/ends with *showing the route this trip started with (vN)*; otherwise it shows the current route. Public feeds always carry `routeVersions` (`{}` for pre-RTE-02 trips).

Lock: the interim edit lock is retired. Editing a versioned route during a live trip is allowed (that trip keeps its pin). Two publishes still wait for the trip on the current or the new bus to end — 409 `ROUTE_LOCKED_ACTIVE_TRIP`: a **legacy** rider-visible route (no `publishedVersion`, nothing pinned; save a draft, publish once the trip ends, and versioning starts) and a publish that **moves the route to another bus** (riders open the route by bus number and would be sent to the other bus's feed while the old trip still runs). Delete and archive are covered below (RTE-03).

Editor: `vN` next to the bus number, *unpublished draft* marker, buttons *save draft (riders keep vN)* / *publish vN+1*, publish disabled with an explanation for the legacy-lock case.

Rules: `python3 scripts/rules-mutations/2026-09-13-route-versions.py`, run after `2026-09-13-route-publish.py` (asserts the route `status` clause exists and refuses to run twice). Emulator tests cover versions, drafts and the feed pin. Part of the unpublished 13 Sep payload; nothing in live data changes — existing routes keep working as legacy (no version) until an admin publishes them once.

AC-19 verification (`artifacts/api-server/src/routes/buses.test.ts`, `scripts/src/firebase-rules.test.ts`, `artifacts/pu-transit/src/pages/student.test.tsx`): a trip started against v2 keeps `{ routeId: 2 }` while the admin publishes v3 without a 409; the rider on that trip sees v2's stops with the note, a rider with no trip sees v3; legacy publish during the trip is refused, its draft is not; Rules refuse a sample that changes, grows or drops the pin.

## Archive and delete (RTE-03, ADM-04 / AC-20, AC-22)

Two ways out of a route, decided by the node's `status`:

- **Archive** — `POST /routes/{id}/archive` (admin) for a published route (legacy ones included). The node is rewritten with `status: archived`; content, `publishedVersion`, every `routeVersions` snapshot and any pending `routeDrafts` entry stay. Riders' `GET /routes` already filters to `published`, so the route leaves search; version reads keep working for history. Idempotent on an archived route. Audit `route.archive`. There is no separate restore: edit the archived route and *publish* — it comes back as the next version.
- **Delete** — `DELETE /routes/{id}` only while `status` is `draft`, i.e. never published; anything else answers 409 `ROUTE_PUBLISHED` ("archive it instead"). Rules mirror this (`2026-09-13-route-archive.py`: a `routes/{id}` node can be removed only while its status is `draft`; legacy nodes without a status cannot be removed; a node that exists as anything but a draft can never be set back to `draft`, and `publishedVersion` can never be dropped — so the guard cannot be sidestepped by demoting first). `RouteInput.status` is `draft | published` only; `archived` is never a save input. Archiving a draft answers 409 `ROUTE_NOT_PUBLISHED` ("delete it instead").
- **Live trips (AC-20)** — archiving is refused with 409 `ROUTE_LOCKED_ACTIVE_TRIP` while the route's bus has a live trip: riders on it follow this route (pinned, or live for legacy routes) and would lose it from search mid-trip. Deleting a draft is never blocked by a trip — Start pins only published versions and riders never see drafts.
- **Editor (AC-22)** — draft rows show *delete*, published rows show *archive*, archived rows neither (edit + publish restores). Both open the same inline confirmation stating the consequence (draft: never seen by riders, cannot be undone; archive: gone from search, versions kept, publish again to bring back); *keep it* changes nothing. During a live trip the archive button is disabled with the explanation; the draft's delete stays enabled. An API refusal is shown inline on the row.

Rules: `python3 scripts/rules-mutations/2026-09-13-route-archive.py` after `route-versions.py` (adds the delete guard and the `route.archive` audit action; refuses to run twice). Part of the unpublished 13 Sep payload; nothing in live data changes.

Tests: `buses.test.ts` (delete of a published route refused, archive hides from students and keeps versions and the draft, republish restores as v3, draft archive refused, draft delete 204, live-trip archive refused with the explanation while the same bus's draft can go), `firebase-rules.test.ts` (published and archived nodes cannot be removed, a draft can), `routes-tab.test.tsx` (buttons per status, cancel changes nothing, archive and delete calls, inline API error).

## Known limits

- Never-published drafts still live in `routes/{id}` (status draft) and are hidden by the API only; Rules grant approved members read access to the whole `routes` node, so a member reading RTDB directly can see them. Edits of published routes are confidential (`routeDrafts` is admin-only). Moving new drafts into `routeDrafts` too is left for later.
- The archive lock is an API precheck like the legacy-publish lock and the FLT-03 deactivation lock (Rules do not read tracking state; a Start racing the archive write, or an admin writing RTDB directly, is not caught); the admin list does not fold archived routes away — they stay in the list with the *archived · hidden from riders* marker.
- `buses:migrate` leaves archived routes alone (a note in the report): they are hidden, and publishing one again runs the registered-bus check in the editor anyway.
- Publishing an archived route again during a live trip of its bus is allowed: that trip never pinned it (Start skips archived routes), so riders who pick it see the current content — the same as a brand-new route published mid-trip.
- The 150 m stop-to-path check is API-only; Rules check only that an `ors` route has some geometry.
- Rules cannot count children or enumerate routes, so a driver client writing RTDB directly could omit a pin at Start or drop a single key later (never forge one); riders then see the current route, as on pre-RTE-02 trips. The API never does either. Rules also do not check that the snapshot's `n` equals its key; the API always writes them together.
- The legacy-route publish lock is an API precheck: a Start that lands between the check and the write leaves that one trip on mutable content, as every trip did before RTE-02.
- `buses:migrate` refuses to rewrite a route with an unpublished draft (the admin list merges the draft over the node) and strips `publishedVersion`/`hasDraft` before resubmitting; a rewrite of a versioned route publishes a new version.
- Draft saves of a published route respond with the merged object without a read-back.
